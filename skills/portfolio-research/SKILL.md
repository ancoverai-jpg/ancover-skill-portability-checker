# Ancover portfolio research

Trigger examples: "Research the next Ancover Skill"; "Run the daily Ancover open source cycle." Non-triggers: "Promote my app on social media"; "Explain what MCP means."

Inspect the existing portfolio ledger and open issues first. Prioritize defects, security problems and maintenance before new products. Reuse existing architecture and group related features; do not create duplicate repositories.

Use available Ancover discovery, inspection and comparison tools when relevant. First verify which tools are actually callable. An internal error means unavailable, not an empty catalog. Public discovery results, declarations, static audits and mock simulations are distinct evidence types; none proves execution or safety. Use public GitHub issues and official documentation as a fallback. Never send credentials or private source code to public search.

For each candidate, record audience, task, consequence, dated source links, independent authors/communities, alternatives, proposed gap, dependencies, risks, effort, enterprise relevance and confidence. Require at least three independent reports across at least two communities before qualifying demand. Count cross-posts and duplicate discussions once. Closed issues are historical context; check current alternatives and do not claim an old defect remains unresolved. Mark insufficiently supported ideas as hypotheses.

Rank with justified editorial scores for pain, evidence, competitive gap, demonstrable value, adoption, Skill fit, enterprise use, maintenance and Ancover fit. Specify the top three; build one complete pilot before expanding. A specification states workflow, inputs/outputs/permissions, exclusions, acceptance criteria, evaluation, demo and maintenance.

For a release, review the exact file set for secrets, private data, dependencies and licenses. Validate isolated installation, representative execution, invalid inputs, trigger behavior, preservation of settings, update and uninstall separately in Codex and Claude Code. Report NOT_TESTED explicitly. Compare useful output with a predeclared baseline when claiming improvement. Partial coverage is experimental. Blocking defects stop publication.

Use English documentation plus Brazilian Portuguese README, reproducible examples, security policy, contribution guide, changelog and roadmap. GitHub publication requires a confirmed destination and working write permissions. Never change an existing private repository to public. Prefer PRs for existing projects. Repository publication and marketplace approval are separate.

Persist decisions and artifact references through discovered → researched → prioritized → specified → developing → validating → ready → published → maintenance. Use an exclusive cycle lock, atomic writes, bounded retries and resume existing work. The user has set a target of at least five distinct new projects or Skills actually published to GitHub per day in America/Sao_Paulo. This replaces the previous weekly cadence and publication cap. Count verified remote commits and individual Skill paths; do not count drafts, private plugin saves, version-only updates or duplicates. Related Skills may share a repository. Work daily in five windows at 09:00, 12:00, 15:00, 18:00 and 21:00; each window has up to 45 minutes and two attempts per failing external action. Keep demand and quality gates intact, record actual output and deficits, and never invent publications to meet the target. Do not buy services or make paid API calls without explicit authorization. The time limit stops new work and saves a resumable handoff; it does not make unfinished work ready.

Notify only publications, material failures or necessary decisions; remain quiet when nothing actionable changed. Prepare launch copy but do not send messages, post promotional issues or publish to social networks without specific authorization. Report measured metrics separately from estimates and do not promise enterprise adoption.

Output a Markdown decision report, structured opportunity data and ledger changes with exact evidence types, unresolved gates and next actions. If scheduling is unavailable, deliver a manual command and state that recurrence is inactive. A schedule file alone is not proof of activation.
